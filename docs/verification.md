# Verification status

This document describes observed results, not release promises.

The desktop application is an unsigned development preview. Current and historical evidence are separated below. Live streaming sessions, interactive tray/autostart behavior and cross-platform upgrade coverage remain separate verification boundaries.

Azure retirement evidence and the private source snapshot are stored outside this public repository. Production data is intentionally not being migrated.

## Discord voice regression fixes — 2026-10-08

A live native Discord test on NixOS verified the configured channel, sent and fetched a labeled test message, joined voice, and played a 7.337-second Azure clip. The listener confirmed full playback, intentional interruption, and complete recovery playback. The receive path processed 1,069 decoded frames and detected the owner's wake phrase three times. Shutdown cleared the voice session, participants, VAD and keyword recognizers; a separate Discord REST check confirmed departure. This first probe deliberately exercised the audio library without the agent, so its wake detections did not produce acknowledgement sounds or replies.

The subsequent full Engine test produced an audible wake chirp but failed transcription: the implementation hardcoded `whisper-1`, which the configured OpenAI project did not allow. Transcription now uses an explicit voice model setting, independently of streamer captions, and reports model-access failures without echoing private provider error details. The shared HTTP helper has regression coverage for selected models reaching the multipart request, current versus legacy language parameters, cancellation before dispatch, and failed model access without an automatic fallback or retry.

The voice lifecycle now connects the retained heard, timeout and cancellation sounds, restores original wake/heard gain factors, interrupts playback for an admitted owner wake, and suppresses duplicate active wake requests. Silence expires after 16 seconds; the first voiced frame starts the original 20-second forced-finalization deadline. Native coverage verifies that pending PCM precedes exactly one finalization even when deadline callbacks repeat. Thinking playback uses stable per-turn variants and two-clip batches during permitted model and tool work. Cue ownership tests cover delayed task scheduling, cancellation, shutdown and delivery boundaries. Automatic follow-up listening remains unimplemented.

A subsequent full Engine test transcribed the owner's question using `gpt-4o-transcribe` and delivered a completed spoken answer using `gpt-5.6-sol`. The listener confirmed that answer and reported the missing thinking sound. Its saved delivery policy allowed speech but disabled public progress, exposing an incorrect coupling between those two controls. Thinking now follows permission to speak at the source. Wake-triggered requests additionally play content-free processing audio during transcription and initial delivery classification; silent/private classification stops it. Text and DM requests remain quiet before classification. This early processing cue is a deliberate extension of the old feedback, not a claim that the old application played audio before classification. A zero thinking-volume setting suppresses it throughout.

Before the subsequent structured-loop audit, the changed source passed 118 core tests, 47 audio tests, six desktop tests and 30 frontend tests. Four explicit native-resource tests were not part of that unit run. Svelte checking reported zero errors and warnings; changed-file formatting and diff checks passed. The later thinking-feedback regression passed 29 focused runtime tests, including emitted cue events and generated WAV bytes for speech enabled with public progress disabled. Installer and final live-cue checks remain separate from these source checks.

New installations default to `gpt-6-astra` for reasoning, `gpt-transcribe` for voice/caption transcription, and `gpt-image-2.5-sunburst` for images, following the [model catalog](https://developers.openai.com/api/docs/models), [transcription guide](https://developers.openai.com/api/docs/guides/transcription), and [image tool guide](https://developers.openai.com/api/docs/guides/tools-image-generation) checked on this date. Saved model choices survive upgrades. Model availability is project-specific; the application does not silently substitute another model when access is denied.

## Structured agent loop preservation — 2026-10-08

The audit compared the old executable turn engine, delivery session, protocol validation, continuations and recovery with the native shared loop. It confirmed ordered multi-round tool calls, provider-issued call identities, immutable delivery policy, durable questions, retained call/round budgets, untrusted tool-result placement and semantic final message groups. It also found and corrected missing behavior: spoken progress, voice finals unnecessarily copied into text chat, strict terminal-envelope gaps, interrupted-turn continuation, setup-access continuations, and lost partial-delivery receipts.

Crash recovery now uses the normal requester-owned queue when a session starts. Saved completed calls supply their recorded result; an interrupted effect supplies an explicit unknown result without being dispatched again. Fresh audited reads can inspect state. Unknown actor-local memory/reminder creations do not block unrelated users, while shared mutations retain their uncertainty guard. Original ownership, provider identity, channel and current permissions are rechecked. Earlier preview records cannot prove whether an interruption was an explicit cancellation, so those ambiguous records remain available for inspection rather than automatic continuation.

The dashboard offers an explicit retry for eligible interrupted requests and projects only bounded delivery status, destinations, message IDs and part counts from saved receipts. It does not expose raw checkpoints, arguments, provider errors or credentials. Cancellation or a crash during a send can still lose acknowledgements that had not reached the saved result; that outcome remains unknown and is not retried automatically. See [agent behavior](agent-architecture.md) for the tested contracts and the remaining feature differences, including wake-required spoken answers and limited image-input/destination support.

The combined source passed 163 core tests, 47 audio tests and six desktop tests, plus 30 interface tests. Four native-resource tests remained explicitly opt-in; Svelte checking reported zero errors and warnings. The actual native `agent_probe` then completed with `gpt-6-astra`: OpenAI accepted all 68 tool schemas and the strict terminal format, and the shared loop finished in two requests and one local configuration call (7,377 ms). Its reply survived reopening the isolated SQLite database. Separate API checks accepted a WAV transcription with `gpt-transcribe` and completed an image-generation tool call using `gpt-image-2.5-sunburst`. These bounded probes do not establish every platform tool or the application's complete managed-image workflow.

The following full Engine test accepted `gpt-transcribe` audio and a `gpt-6-astra` tool response, and the listener heard the thinking cue. It then aborted with a Tokio worker stack overflow while dispatching `configureTurnDelivery`; it delivered no answer. The interrupted ledger retained that started call. A separate Discord REST check confirmed the bot had departed after the crash. An offline test reproduced the failure through the real Engine queue. Owning dispatch futures on the heap now keeps the same queue/tool/cue path within an ordinary 2 MiB worker stack, without increasing production stack sizes. The regression and all 167 core tests passed after the fix; a subsequent live check remains necessary.

The same investigation found that the native keyword event's audio buffer was discarded before capture began. The desktop now retains the original 1.5-second PCM preroll so words spoken immediately after the wake phrase survive recognition latency. Tests cover ordering before later streamed frames, the bounded tail, sample alignment and cancellation. The earlier live wake-to-heard delay occurred before transcription; without per-frame finalization evidence its precise cause is not established by these logs.

The corrected full Engine completed the live settings question with `gpt-transcribe` and `gpt-6-astra`: five model rounds, four completed tools (delivery configuration, current settings, voice options and connected capabilities), and a completed spoken answer identifying the configured Buddy/Azure Guy Neural voice. The transcription preserved the settings question but misrecognized its prefix as an additional page-opening request; the response correctly stated that it could not open the page and made no settings changes. Emitted and completed speech establishes application playback progress; the listener's confirmation and packaged-build checks are tracked separately.
